# Assistant

Status: approved
Created: 2026-11-11 21:12
Inspired by: [shepherdr](https://github.com/eliasstravik/shepherdr)

## Goal

One AI Assistant, running 24/7 on a cloud VM, that you message to control every herdr session on
every machine in your tailnet. It reads your projects, turns what you write into tasks, starts each
task as a coding agent on the right machine, and brings back only what needs you.

## Decisions

| # | Decision |
|---|----------|
| 1 | The Assistant is an AI coordinator, not just a machine dashboard. |
| 2 | It is a coding agent (Claude Code or Codex) in a herdr pane on the VM, not a new chat backend. Ovis stays a bridge. |
| 3 | The VM only coordinates. Tasks run on your own machines, never on the VM. |
| 4 | The VM reaches machines through herdr's own machines (`herdr machine add <alias> ssh://user@<tailscale-name>`), SSH over Tailscale. |
| 5 | You bring the VM and run one install script on it. The script prompts for the Tailscale machine name. |
| 6 | Ovis runs on the VM too, on `127.0.0.1` behind `tailscale serve` (HTTPS). That is the 24/7 entry point. |
| 7 | Tasks have the full lifecycle: queue, schedule, fresh-eyes review, merge. Each part is optional per task. |
| 8 | A task lands as a GitHub PR by default, or as a local merge when the repo has no GitHub remote. |
| 9 | There is one global Assistant for every machine and project. |
| 10 | The Assistant reads files only inside registered project folders. All writes happen through tasks. |
| 11 | The read limit is enforced by the `ovis-task` CLI. The agent's permissions allow only `ovis-task` and deny raw `ssh` and `herdr`. |
| 12 | An app-level toggle switches between two modes, **Assistant** and **Code** (today's Ovis). Assistant mode is a fresh UI in the same themes. |
| 13 | The toggle always shows. On an Ovis that is not the Assistant VM, Assistant mode is a setup page. |
| 14 | Only you add projects, in the UI. The Assistant can list projects but never add them. |
| 15 | Each machine has a "max running tasks" limit (default 3). Tasks can wait for another task, run at a set time, or repeat by cron. |
| 16 | Maintenance means watch and report. Fixes happen only on your click, and the queue resumes by itself when a machine comes back. |
| 17 | Task agents run full auto (`--dangerously-skip-permissions` / Codex full-auto). |
| 18 | State lives in files, not the chat. Assistant sessions are replaceable and named by their start timestamp. |
| 19 | Six phases, one PR each (below). |

## Scope

- In: install script, mode toggle, setup page, machines and projects, Assistant chat sessions,
  `ovis-task` CLI, tasks in worktrees, task board, `Needs you` cards, web push, queue, schedule,
  cron, review, PR or local merge.
- Out (later): a cloud provider API that creates the VM; setup of the VM from the browser over SSH;
  an Assistant shown live inside a local Ovis through a proxy; restricted SSH accounts per machine;
  per-project Assistants; voice.

## Architecture

```
phone / laptop browser
        │  https://<name>.<tailnet>.ts.net   (tailscale serve)
        ▼
┌──────────────── cloud VM (24/7) ────────────────┐
│ Ovis server (127.0.0.1)   herdr                  │
│  ├─ Assistant mode UI     └─ Assistant agent pane│
│  ├─ machine watcher (30s)        │ only tool:    │
│  ├─ queue + clock                ▼               │
│  └─ stateDir/assistant/     ovis-task CLI        │
└──────────────────────────────────┬───────────────┘
                                   │ herdr machines, SSH over Tailscale
             ┌─────────────────────┼─────────────────────┐
             ▼                     ▼                     ▼
       laptop (herdr)       home server (herdr)     other PC (herdr)
       task agents in git worktrees, full auto
```

### State on the VM (`stateDir/assistant/`)

- `projects.json`: `{ id, machine, path, mergeMode: "pr" | "local", defaultAgent }`. Written only
  by the UI.
- `tasks.json`: `{ id, title, brief, project, status, paneId, worktree, branch, after?, at?, cron?,
  review: boolean, autoMerge: boolean, prUrl?, createdAt }`.
- `machines.json`: per-machine settings that herdr does not hold (`maxRunning`).
- `sessions/`: one entry per Assistant session, named `YYYYMMDD-HHMM`, holding its pane and archive.
- `notes.md`: the Assistant's own notes, read at the start of every session.

Write every file atomically with mode `0600`, as `herdr-profile-state.json` is today.

### Task statuses

`To do` → `Queued` → `Working` → (`Needs you` ↔ `Working`) → `Ready` → (`Reviewing`) → `Merging`
→ `Done`. `Scheduled` before `Queued` for timed tasks, and `Cancelled` or `Failed` at any point.
`Working` and `Needs you` come from herdr's agent state of the task's pane.

### `ovis-task` CLI (the Assistant's only tool)

- `ovis-task projects` lists projects (read only).
- `ovis-task read <project> <path>`, `ovis-task grep <project> <pattern> [path]` and
  `ovis-task git <project> log|diff|status|show` read files. Each one resolves `..` and symlinks
  on the remote side (`realpath`) and refuses anything outside the project folder before it runs.
- `ovis-task create <project> --title --brief [--after ID] [--at TIME] [--cron EXPR] [--review]
  [--auto-merge] [--agent claude|codex]`
- `ovis-task list [--status S]`, `ovis-task show <id>` (the task's recent pane output)
- `ovis-task answer <id> <choice>`: goes through the prompt-answer endpoint, never guessed keys.
- `ovis-task cancel <id>`
- `ovis-task approve <id>` stays UI-only: the CLI refuses it, so the Assistant cannot merge on its
  own. The one exception is a task created with `--auto-merge` whose review passed.

The CLI talks to the VM's Ovis server on loopback, so the server alone holds the logic and state.

## Phases

### Phase 1: Base

- `scripts/install-assistant.sh` (Linux x64/arm64). It prompts for:
  1. the Tailscale machine name (`tailscale up --hostname=<name>`, default `ovis-assistant`)
  2. the Tailscale login (prints the auth link, or takes a pasted auth key)
  3. the Assistant agent CLI (Claude Code or Codex), then signs it in

  It then installs herdr, Bun and Ovis, writes systemd user units for the herdr server and Ovis
  (bound to `127.0.0.1`), and runs `tailscale serve` in front of it. It ends by printing the HTTPS
  address. It supports `--dry-run`, and running it again is safe.
- The server marks itself as the Assistant VM (for example, `OVIS_ASSISTANT=1` set by the unit)
  and tells the client so.
- The client gets an app-level **Assistant | Code** toggle in the header, remembered per device.
  Code mode is unchanged.
- An Ovis that is not the Assistant VM shows a setup page in Assistant mode: what the Assistant
  is, the install command, and a field for the VM's address that becomes a link.

### Phase 2: Machines and projects

- The Assistant-mode sidebar has a **Machines** section, filled from `herdr machine list --json`
  (reusing the herdr-profiles discovery the Remote PCs code already has).
- A watcher runs every 30s per machine: SSH is reachable, herdr is running, the agent CLI is
  installed, `gh` is signed in (when any of its projects merges by PR), and task panes are still
  there. Failed checks back off as discovery does.
- Problems show on the machine row with a fix button (**Start herdr**, **Restart agent**). Nothing
  runs without your click.
- **Add project** (UI only) takes a machine and a folder path. The server checks that it exists,
  is a git repo, and is not `/`, `~` or a parent of the home folder. A GitHub remote means
  `mergeMode: "pr"`, otherwise `"local"`. You can edit or remove a project.
- There is a per-machine **Max running tasks** setting.

### Phase 3: Assistant chat

- The Assistant is an agent pane in herdr on the VM, started in a dedicated folder that holds its
  instructions file (`AGENTS.md` / `CLAUDE.md`) and agent settings.
- Agent permissions allow `Bash(ovis-task:*)` and reading its own folder, and deny `ssh`, `scp`,
  `herdr`, `curl` and edits outside its folder. Codex gets the same allowlist.
- The instructions file says: call `ovis-task list` and read `notes.md` first; the state lives in
  `ovis-task`, not in memory; write lasting facts to `notes.md`.
- The page has the chat in the middle (the existing chat view pointed at that pane) and the task
  board on the right (empty until phase 4).
- A **New session** button starts a fresh pane named by its start timestamp (`YYYYMMDD-HHMM`).
  The previous one is archived and readable in the sidebar's **Sessions** list.
- This phase ships `ovis-task projects/read/grep/git`, with tests for path escapes: `..`, symlinks
  out of the folder, absolute paths, and a project that was removed.

### Phase 4: Tasks

- `ovis-task create/list/show/answer/cancel`.
- To start a task, on the project's machine: `herdr worktree` creates a worktree on a branch
  `assistant/<id>-<slug>`, then an agent pane opens in it in full-auto mode with the brief as its
  first prompt. herdr's own focus is never moved.
- The task board has columns `Needs you`, `Ready`, `Merging`, `Working`, `Queued`, `Scheduled` and
  `Done`. Clicking a task opens its pane in Code mode's normal pane view.
- Questions, plan approvals and merges from a task's agent come as `Needs you` cards, answered
  through `POST /api/pane/prompt/answer`.
- Web push (the existing push code) fires when a task enters `Needs you` or `Ready`.

### Phase 5: Queue and schedule

- The queue lives in the VM's Ovis server. A task starts when its machine has a free slot, its
  `after` task is `Done`, and its `at` time has passed.
- Cron tasks create a new task at each fire time. The clock state is in `stateDir`, so a restart
  neither double-fires nor loses a run.
- A task on a machine that is down stays `Queued`. When the machine comes back, the queue resumes
  by itself.

### Phase 6: Review and merge

- With `review` on, a task that reaches `Ready` gets a second, fresh agent pane in the same
  worktree. It reviews the diff against the base branch and reports pass or findings. Findings go
  back to the task agent and the review runs again, up to N rounds.
- For a `pr` project, the task agent pushes its branch and opens a PR with `gh`. **Approve** runs
  `gh pr merge` on that machine.
- For a `local` project, **Approve** merges the branch into the checkout's base branch. A conflict
  becomes a `Needs you` card and never a forced merge.
- `autoMerge` merges once the review passes, without the approve click.
- After a merge, the worktree and its branch are removed.

## Known risk: full-auto task agents

Task agents run with permission checks off. A task can do anything your user account can on that
machine: read secrets, push anywhere, delete files outside its worktree. The worktree is a
convention, not a sandbox. What is left to guard it:

- tasks only start from your messages to the Assistant, or from cron entries you made
- fresh-eyes review before merge (turn it on for anything that matters)
- nothing merges without your approval unless the task was created with `--auto-merge`
- the Assistant itself is **not** full auto: it is fenced by the `ovis-task` allowlist

A safer default can come later (edits inside the worktree allowed, everything else asks) as a
per-project setting.

## Touches

- `scripts/install-assistant.sh` (new)
- `server/`: an Assistant module (state files, machine watcher, queue and clock, task runner,
  review and merge), HTTP routes for the UI and `ovis-task`, the Assistant-VM flag. It reuses
  the herdr-profiles discovery, the SSH transport of Remote PCs, prompt answer and push.
- `shared/`: the wire types for projects, tasks, machines' health and sessions.
- `src/`: the Assistant | Code toggle, the Assistant-mode layout (sidebar with Machines, Projects
  and Sessions; chat; task board), the setup page, and i18n entries for all new strings.
- `bin/ovis-task` (new) and the Assistant's instructions and settings templates.
- herdr API: `herdr machine list`, `herdr worktree`, pane create/read and agent state,
  `events.subscribe`.

## Checks

- Every phase: unit and contract tests with an isolated herdr test session, a `mkdtempSync`
  `stateDir` and `port: 0`. Never the user's real herdr or machines. Run `bun run check fast` before
  each push.
- Phase 1: the install script under `--dry-run` in CI. A real run on a throwaway VM.
- Phase 3: path-escape tests for `ovis-task` (above). A test that the agent settings deny `ssh` and
  `herdr`.
- Phase 4–6: state-transition tests for the queue, `after`, `at`, cron (no double fire across a
  restart), a machine going down and coming back, review rounds, and a merge conflict.
- Manual QA: a VM plus two test machines on a tailnet, with a demo repo. Never the maintainer's
  live sessions.
- A `changelog.d/` fragment for each user-facing phase.

## Open questions

- ~~Which herdr API starts a pane on a remote machine?~~ Answered 2026-11-11: use the Remote PCs
  bridge (`/api/machines/:id/...`, `server/machine-api.ts`). `worktree/create` launches the agent
  (`server/workspace-routes.ts`), then `pane/input` sends the brief (that route takes no first
  message yet). `MachineManager.observe` (`server/machines.ts`) streams `agent_status`, and
  `pane/prompt/answer` answers cards. The task runner calls the bridge from inside the server via
  `manager.endpoint(id)`. Each machine needs the bridge installed and one **Connect** approval.
  `herdr --machine <alias> ...` is the fallback for a machine without the bridge (polling only).
- Windows machines (noted in phase 2): the health and folder checks are POSIX `sh` over SSH, so a
  Windows PC in herdr's catalog shows as unreachable. Phases 3–6 (`ovis-task read/grep/git`, task
  start) need PowerShell variants, or the Assistant should leave Windows PCs out.
- **Restart agent** (phase 2's second fix button) only has a meaning once tasks exist: phase 2
  ships **Start herdr** and a stubbed task-pane check; phase 4 adds the check and that button.
- The review round limit N (suggest 3).
- Whether **Approve** is ever allowed from a phone without a second confirmation.
- Do the agent CLIs' full-auto flags still read a per-worktree settings file, so a later safer
  default can be set per project?
- Codex gap (phase 3): Codex has no allow/deny list as Claude Code's `permissions` is. The
  Assistant's Codex runs with `--ask-for-approval untrusted --sandbox workspace-write` (writes stay
  in its folder) and an execpolicy file, `.codex/rules/ovis-task.rules` in its folder, that allows
  `ovis-task` and forbids ssh, scp, herdr and curl. Whether Codex loads rules from a project's
  `.codex/` (not only `~/.codex/rules`) is unverified, so without it every command but `ovis-task`
  asks the user instead of being refused. Codex cannot limit reads to its folder, and the sandbox
  needs network on so `ovis-task` reaches loopback. Claude Code uses `defaultMode: "dontAsk"`, which
  refuses anything outside its allow list.
- `notes.md` lives in the Assistant's folder (`stateDir/assistant/agent/notes.md`), not
  `stateDir/assistant/notes.md`: the agent may edit only its own folder.
- The button is **New chat**, not **New session**: the UI wording rule (src/conventions.test.ts)
  keeps "session" for herdr's session and an agent's history.
- Phase 4: `ovis-task create` runs on the VM, but a task agent on another machine has no
  `ovis-task` and no route back, so its `Needs you` and `Ready` come only from herdr's agent state
  through the Remote PCs bridge. A task's brief should not tell it to call `ovis-task`.
- Phase 4 shipped the brief as the agent's command-line prompt (`-- <brief>`), with line breaks
  joined into spaces: a create route's `first_message` is held until a page that asked sends it,
  so it never goes unattended. A multi-line brief needs a bridge path that may send one first
  message with no page (phase 5's queue starts tasks with nobody watching either).
- Phase 4 tasks get no extra push: Remote PCs already pushes every remote pane's `blocked` and
  `done` under each device's notify policy, titled by the pane, not the task. A task-titled push
  would need its own tag so the two do not both arrive.
- Phase 5: a task's `id` is the next number in `tasks.json`; cron-made tasks will raise it fast,
  which is fine, but `after` must then refer to a task id, not a cron entry.
- Phase 6: a pane gone from a Ready task leaves it Ready (its work is done), and cancel keeps the
  worktree; merge and cleanup must remove both, and a Failed task's worktree too.
- Phase 5 shipped `--after` waiting for `Done`, which only phase 6's merge sets: until then an
  `--after` task waits for good. Phase 6 should set `Done` after a merge (and decide whether a
  `local` task with nothing to merge goes from `Ready` to `Done`).
- Phase 5: the queue's clock is the watcher's 30 s check of each machine, so an `at` or cron time
  is seen within one interval, later while that machine backs off (its task could not start
  anyway). A cron template keeps its next fire time (`next`) in `tasks.json`, written with the task
  it fires. `Cancel` on a starting task is refused for that moment, not queued.
- Phase 4–5: the Assistant pane is not restarted when herdr or the VM restarts; the chat then says
  the pane is not open and **New chat** starts another. Whether the queue should restart it is open.
